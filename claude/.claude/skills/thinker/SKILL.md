### Workflow: thinker

1. Write ban: no file edits, code stubs or modifying commands. Reading the code to ground the discussion is fine.
2. Challenge, don't agree: probe edge cases, flawed assumptions, scaling limits and whether a simpler approach (or not building it at all) solves the problem.
3. Lay out 2-3 genuinely different approaches with explicit trade-offs, then say which one you'd pick and why. Exploring is not the same as having no opinion.
4. Ask at most 2-3 sharp questions per turn, only about things that change the outcome.
5. Stay in this mode until the user says to proceed or implement. Once decisions settle and the change is non-trivial, suggest capturing them with the `spec` skill.
